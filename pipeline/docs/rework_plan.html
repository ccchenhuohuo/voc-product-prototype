管道改造计划

七项改动，三个阶段。核心是把「分类由渠道决定」这个结构性错误改掉，同时把被过度过滤掉的数据放回来。

2026-08-16 · 全部量级为库内实测 · 配套〈数据管道重构〉与〈VOC 数据架构〉

1要改什么

按对数据的影响排序。标签表示改动性质：纯 SQL 秒级生效，改代码 + 重跑抽取 分钟级，需重跑生成 小时级。

#改动现状 → 目标性质
1分类改由内容判定 opp_type 由渠道写死 → 由证据内容三分类重跑生成
2去掉星级过滤 生成池 4,232 → 6,500（放回 2,268 条）重跑生成
3社媒接入老品迭代 接入 1,373 消息 / 12,478 证据（含 658 负面）纯 SQL
4条目阈值维持 ≥2 不改。降到 1 会让条目涨到 747、多数是单条抱怨，队列被淹没的代价大于覆盖收益不改动
5SPU 编码规范化 社媒匹配 27 → 31（MT-79 ↔ MT79）重跑抽取
6排除第三方型号 剔除 NP-FZ100 EN-EL15 等相机电池型号重跑抽取
7来源线口径统一 代码、文档与机会层来源值统一为 电商 / 社媒；channel 保持需求缺口 / 竞品对标代码 + 迁移脚本
💡

只有 #1 和 #2 需要重跑 LLM，但它们必须一起跑——都改的是生成池与生成逻辑，分两次跑等于白跑一次。其余五项加起来几分钟。

2为什么必须打包做

这七项不是七件独立的事，它们咬在同一条链路上。分开做会互相推翻。

  • #5 #6 必须在 #3 之前——社媒接入老品迭代靠 SPU 匹配，编码没规范化、第三方型号没剔除，接进来的就是脏数据。
  • #7 必须在最前或最后——它碰所有文件。夹在中间做，会和 #1 的改动在同一批文件上冲突。决定放最前：后续所有改动都在新口径上写，避免刚改完又要再改一遍。
  • #1 #2 必须同批重跑——池子扩大 54% 和分类规则改变都只在生成时生效，跑两次是纯浪费 3 小时。
  • #4 不动——条目阈值维持 ≥2。它是展示层口径，改它会和新数据的覆盖率变化混在一起，验收时分不清增量来自哪边；先把数据本身做对，阈值留到有真实效果可看时再单独议。
🎁

顺带清掉一笔旧债：库里有 20 条不可精确回退的融合（12 个机会点被融合、115 条证据打了 match_by='merge'）。全量重跑会重新生成整个机会点层，这批历史包袱自动消失——这是之前判断"不值得单独重跑"而搁置的事。

3三个阶段

每个阶段结束都有一道验收闸门，不过闸门不进下一阶段。验收口径全部在动手之前定死，不允许跑完再补。

阶段一口径替换 + 抽取层修正 改代码 + 迁移脚本 · 本轮不执行

做 #7 来源线口径统一、#5 SPU 规范化、#6 排除第三方型号。全部是确定性改动，不碰 LLM；迁移与数据重跑由验收方另行受控执行。

SPU 规范化落在抽取层（clean.py），不是在查询里临时 regexp_replace。spu 保存消除连字符、空格与大小写差异后的编码，spu_raw 保留上游原值；第三方型号用电商 SPU 集合做白名单反向剔除，未匹配编码进入 spu_unmatched，不静默丢弃。

闸门 A：① 全仓历史临时线名的文本残留为 0；受控迁移 013_src_line_rename.sql 以 Unicode 转义识别历史存量，并断言迁移后的旧口径残留为 0；② 纯函数单测证明 MT-79 与 MT79 归一；③ 第三方型号从 spu 剔除且可在 spu_unmatched 查到；④ pipeline 与 system 两套离线 pytest 均以退出码 0 结束。本阶段不执行 SQL、不连生产库、不重跑管道，因此消息数、证据数、挂靠数及迁移后存量分布留待验收方执行时核验。
阶段二分类改造 + 全量重跑生成 改代码 + 重跑 LLM · 约 3.5 小时

做 #1 分类改由内容判定、#2 去掉星级过滤，然后清空机会点层全量重跑。

分类规则：LLM 依据证据内容三选一——证据主要在讲我们某个在售产品的问题 → 老品迭代；讲竞品的问题或没有对应在售产品的需求 → 新品创新；判不准 → 新品创新 + 打「待人工判定」。渠道不再参与判定。

星级过滤：low_conf 标记保留但不再用于过滤。证据照进生成池，界面上给弱提示，判断权交给 PM。用满意度否定具体抱怨，逻辑本身站不住。

闸门 B：① 生成池实际规模 ≥6,500（证明星级过滤已解除）；② 新的 opp_type 分布中，老品迭代不再等于电商机会点数（证明分类已脱离渠道）；③ 抽样 30 条新品创新人工核对，误分类率 <10%；④ voc_opp_lineage 归零（融合债已清）；⑤ 引文溯源率与重跑前持平或更好（不低于 96%）。
阶段三展开层口径调整 纯 SQL · 分钟级

只做 #3 社媒接入老品迭代。改的是 voc_spu 与 voc_spu_issue 两个物化视图的口径；条目阈值保持 ≥2 不动。

两个视图现在都硬编码 WHERE src_line='电商'，要改成按 SPU 归属而非按渠道收录。社媒证据只有能匹配到在售 SPU 的才进，匹配不上的仍归战略层，不凭空造产品卡。

闸门 C：① SPU 卡覆盖 ≥162 个；② 每张卡的证据数 = 电商证据 + 社媒可匹配证据，抽 3 个 SPU 独立复算比对；③ 阈值仍为 ≥2，且被挡掉的单证据条目在事实层与战略层可全数查到（覆盖度没有因阈值而丢失）；④ 人工表零污染——voc_spu_issue_manual 与审计日志在整个改造期间保持为 0。

4验收方法

不采信任何自报结果。每道闸门的口径都用独立于实现的方式复算。

验收动作怎么做
SQL 体检每次改完 queries.py 跑 check_sql.py，把每条 SQL 拿到真库 EXPLAIN，一条不漏
口径独立复算关键数字（覆盖数、证据数、分类分布）全部绕开实现，用手写 SQL 重算一遍比对
最小探针先行重跑生成前先跑单周探针验证新分类逻辑，通过再上全量——不用全量重跑当探针
人工抽样分类改造后抽 30 条新品创新逐条核对，这是唯一能验证「分类是否真的对」的方法
零残留检查每阶段结束确认人工表、审计表、哨兵周产出全部为 0
⚠️

阶段二开始前必须先备份。全量重跑会清空机会点层，这是本次唯一不可逆的操作。现在的备份是手动打的、落在容器内 /tmp，异地备份至今没配——这是我的运维债，阶段二动手前先补上。
