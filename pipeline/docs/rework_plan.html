管道改造计划

七项改动，三个主阶段（阶段二拆为 2a / 2b）。核心是把「分类由渠道决定」改为「分类由机会点的 SPU 证据挂载决定」，并把代码交付与受控执行明确分开。

2026-08-16 · 全部量级为库内实测 · 配套〈数据管道重构〉与〈VOC 数据架构〉

1要改什么

按对数据的影响排序。标签表示改动性质：纯 SQL 秒级生效，改代码 + 重跑抽取 分钟级，需重跑生成 小时级。

#1 不再交给 LLM 判型。现存机会点由迁移 015_classification_contract.sql 确定性回填，后续生成由纯函数根据完整证据集合分类；#2 才会扩大 LLM 生成池。代码与迁移在 2a 交付但不执行，受控迁移与重跑统一留到 2b。

2为什么必须打包做

这七项不是七件独立的事，它们咬在同一条链路上。分开做会互相推翻。

  • #5 必须在 #3 之前——社媒接入老品迭代靠 SPU 匹配，编码没规范化就对不上号（MT-79 和 MT79 会被当成两个产品）。
  • #6 从「剔除」改成「不筛」——原方案要用电商 SPU 集合做白名单反向剔除第三方型号。实测推翻了这个前提：社媒 2,561 条带 SPU 的消息，brands 100% 含本品；NP-FZ100 是本品 Tagbatt 兼容电池沿用索尼电池规格命名，不是竞品。按原方案执行会为拦 6 条而误删约 1,380 条本品消息。「社媒独有 SPU 要不要成卡」是展示层口径，移到阶段三的 voc_spu 里定，抽取层不销毁数据。
  • #7 必须在最前或最后——它碰所有文件。夹在中间做，会和 #1 的改动在同一批文件上冲突。决定放最前：后续所有改动都在新口径上写，避免刚改完又要再改一遍。
  • #1 #2 的代码必须在重跑前同时就位——#1 可先用迁移重算现存 645 个机会点，且本身不需要 LLM；但 2b 若执行全量生成，必须让扩大后的池子直接使用新的证据集合分类函数，不能再落回渠道判据。
  • #4 不动——条目阈值维持 ≥2。它是展示层口径，改它会和新数据的覆盖率变化混在一起，验收时分不清增量来自哪边；先把数据本身做对，阈值留到有真实效果可看时再单独议。
🎁

顺带清掉一笔旧债：库里有 20 条不可精确回退的融合（12 个机会点被融合、115 条证据打了 match_by='merge'）。全量重跑会重新生成整个机会点层，这批历史包袱自动消失——这是之前判断"不值得单独重跑"而搁置的事。

3三个主阶段

每个阶段结束都有一道验收闸门，不过闸门不进下一阶段。验收口径全部在动手之前定死，不允许跑完再补。

阶段一口径替换 + 抽取层修正 改代码 + 迁移脚本 · 本轮不执行

做 #7 来源线口径统一、#5 SPU 规范化、#6 抽取层不筛 SPU。全部是确定性改动，不碰 LLM；迁移与数据重跑由验收方另行受控执行。

SPU 规范化落在抽取层（clean.py），不是在查询里临时 regexp_replace。spu 保存消除连字符、空格与大小写差异后的编码，spu_raw 保留上游原值，spu_unmatched 只留规范化后为空的无效 token。不按任何名单筛选——云听依本公司产品体系打标，挂到 SPU 即本品。

闸门 A：① 全仓历史临时线名的文本残留为 0；受控迁移 013_src_line_rename.sql 以 Unicode 转义识别历史存量，并断言迁移后的旧口径残留为 0；② 拿真库数据用独立于实现的 SQL 复算：社媒可匹配 SPU 27 → 31，且规范化零碰撞（电商 328→328、社媒 83→83）；③ spu_unmatched 只出现规范化后为空的无效 token，不出现任何有效编码；④ 电商消息数、证据总数、挂靠数三个基线不变（26,407 / 63,972 / 1,638）；⑤ pipeline 与 system 两套离线 pytest 均以退出码 0 结束。
⚠️

闸门口径的教训：原闸门 A② 只写「社媒可匹配 SPU ≥31」，只量了留下多少、没量丢掉多少，因此测不出白名单会误删 1,380 条本品消息。定闸门时两头都要量。

阶段 2aSPU 分类契约落地 代码 + 迁移脚本 · 本轮不执行

做 #1 分类改由 SPU 挂载判定，并补齐生成池、SPU 展开层与清理脚本的安全约束。分类函数只读取该机会点的完整证据集合，按先命中先生效执行：

规则条件结果
R0零条证据classification_state='无效'
R1任一证据所属消息 cardinality(spu) > 0老品迭代 / 确定
R2无 SPU，且证据集合包含社媒来源新品创新 / 确定
R3无 SPU，且证据全部来自电商classification_state='无效'

实现假设（待 2b 受控验证）：R0 / R3 的 opp_type 置为 NULL，不向 opp_type 塞入第三种值；无 SPU 的电商与社媒混合证据，只要包含社媒即由 R2 命中。这两点是当前实现对机会级规则的明确化，不冒充已经执行验证的库内事实。

015_classification_contract.sql 增加 classification_state 与 classify_rule，按 R0–R3 回填全部存量，并用 voc_opp_evidence 实际行数对账全部 evi_total。R0 / R3 只打「无效」标记，不删除机会点或证据；看板按状态排除，诊断链仍完整。

同一迁移重建 voc_spu_issue：用 opp_type='老品迭代' 且 classification_state='确定' 约束机会点，替换旧的纯 m.src_line='电商' 收录口径，使已挂 SPU 的社媒证据可进入对应老品卡；HAVING count(*) >= 2 原样保留。

line_a_pool 排除消息 SPU 为空的电商证据，因为这属于上游数据缺陷，不应继续生成机会点。分类写成不连库的纯函数，并覆盖 R0–R3、跨多 SPU、混合渠道无 SPU 和零证据边界。

rerun_both.sh 的清理段改为单一事务，并启用 set -euo pipefail：任一外键或语句失败即整段回滚，不再留下「关系表已清、机会点仍在」的半清库。本阶段只改脚本，不运行清理、SQL、数据库连接或生成管道。

闸门 B-2a（代码闸门）：① 纯函数与边界单测通过；② 静态检查确认新机会不再使用渠道三元表达式判型；③ 迁移自检写死 264 / 368 / 13 / 645，且 classify_rule IS NULL 为 0；④ voc_spu_issue 同时具备类型与状态约束，阈值仍为 ≥2；⑤ 清理语句处于同一事务。本闸门不执行 015，也不把断言数字写成迁移结果。
⚠️

015 目前只是代码交付，未执行。264 条老品迭代、368 条新品创新、13 条无效、总计 645 是迁移事务内的预期断言，不是本轮已经验证的库内分布。

阶段 2b受控迁移 + 生成重跑 另行授权执行 · 预计约 3.5 小时

由验收方在备份与回退条件具备后，另行执行 015、独立复算分类与证据计数，再决定是否做 #2 去掉星级过滤及全量生成重跑。2a 不自动进入 2b，也不以代码检查替代真实数据库验收。

星级过滤：low_conf 标记保留但不再用于过滤；若批准重跑，证据进入扩大的生成池，而生成出的每个机会点仍由完整证据集合执行 R0–R3。电商无 SPU 证据在池入口即被挡住，不会以 R3 为代价批量制造无效机会。

若受控重跑调用清理脚本，必须先验证单事务回滚行为；R0 / R3 的「无效」标记不是清理指令，不能据此删除机会点或证据。

闸门 B-2b（数据闸门）：① 015 成功时分布严格为老品迭代/确定 264、新品创新/确定 368、无效 13、总计 645，规则空值为 0；② 全部 evi_total 与关系表实际行数一致；③ 独立复算确认 R0–R3 命中顺序和看板无效过滤；④ 重跑若获批准，生成池规模、引文溯源率与分类分布另行记录，不沿用 2a 的静态断言冒充实测；⑤ 任一清理失败均保持原数据完整。
阶段三展开层后续口径调整 纯 SQL · 分钟级

继续做 #3 社媒接入老品迭代的剩余展示层工作。voc_spu_issue 的分类安全约束已前移到 2a，阶段三不再重复改判型契约；条目阈值保持 ≥2 不动。

voc_spu 等后续展示口径按 SPU 归属而非渠道展开。社媒证据只有能匹配到在售 SPU 的才进，匹配不上的仍归战略层，不凭空造产品卡。

闸门 C：① SPU 卡覆盖 ≥162 个；② 每张卡的证据数 = 电商证据 + 社媒可匹配证据，抽 3 个 SPU 独立复算比对；③ 阈值仍为 ≥2，且被挡掉的单证据条目在事实层与战略层可全数查到（覆盖度没有因阈值而丢失）；④ 人工表零污染——voc_spu_issue_manual 与审计日志在整个改造期间保持为 0。

4验收方法

不采信任何自报结果。每道闸门的口径都用独立于实现的方式复算；涉及 SQL、真库与管道的动作全部属于 2b 或后续阶段，本轮 2a 不执行。

验收动作怎么做
SQL 体检每次改完 queries.py 跑 check_sql.py，把每条 SQL 拿到真库 EXPLAIN，一条不漏
口径独立复算关键数字（覆盖数、证据数、分类分布）全部绕开实现，用手写 SQL 重算一遍比对
最小探针先行重跑生成前先跑单周探针验证新分类逻辑，通过再上全量——不用全量重跑当探针
人工抽样分类改造后抽 30 条新品创新逐条核对，这是唯一能验证「分类是否真的对」的方法
零残留检查每阶段结束确认人工表、审计表、哨兵周产出全部为 0
⚠️

进入阶段 2b 前必须先备份。阶段 2a 只交付代码与迁移文件，不执行 SQL、不连库、不清理数据、不重跑管道。全量重跑涉及机会点层重建，必须由验收方另行受控授权；R0 / R3 的无效行始终按标记保留，不因分类迁移物理删除。
