## 1. 老品迭代管道 v3

### 1.1 目的

服务**产品页**，回答：**这个 SPU 现在有哪些问题、各有多少人在说。**
PM 的使用场景是「打开某个产品，看它的问题清单」，而不是「看某个问题横跨哪些产品」——
后者是战略视图的诉求，不应反向约束本管道的身份设计。

### 1.2 流程

```
G 系列 · 证据入池（v2 现状，不改）
  电商：R3 契约 —— e.is_product ∧ 负面 ∧ 非空 snippet ∧ 必挂事实 SPU
  社媒：G1 品牌白名单 → G1b 组传染 → G2 标签门 → G3 官号门
        → G4 价值门（完整正文 + 父帖标题）→ G5 有 SPU 者进老品
        （spu ∪ spu_inherited；无 SPU 的缺陷落「缺陷不可归属」终态）
                            ↓
归属快照冻结【本轮新增，见 §4.2】
  按 run_id 固定一次 (message_id, seq) → assigned_spu[] 的展开结果
  本轮的路由、生成、派生、验收全部读同一份快照
                            ↓
L1 · SPU 圈定【身份分块，本次核心改动】
  按冻结快照把证据归到 SPU 名下
  · 两来源在此天然混合，不存在「分开处理再缝合」
  · 多 SPU 消息（消息级实测 14.2%）落进每个被提及的 SPU 块——
    一条同时抱怨 A 和 B 的评论确实同时构成两边的证据，是语义不是缺陷
  · 扇出倍率 F/U 为待采量，见 §5；**不得用 14.2% 直接推算总行数**
                            ↓
L2 · SPU 内问题聚合【主聚合层】
  规模实测（全量池，029 后）：285 个 SPU / 7,558 扇出行，
  中位 9 条，p90 59 条，最大 419 条，Stage1 批次 361
  · 90% 的 SPU 单批（BATCH_SIZE=50）直接分组，无需粗筛
  · 共有标签作提示词特征 —— **已 A/B 实测无效，不实现**（§7.1）
  · >50 条的热门 SPU（全量池实测 35 个，占 12.3%）先粗切多批，批间用模式名向量合并回收
    （沿用 stage1.py:387 现有机制，**`MODE_MERGE_COS` 0.85 → 0.75**）。
    该阈值仅作召回、判定仍交 L3（`config.py:184` 原注释）——
    误合并有 L3 兜底，无保护的是漏合并：余弦低于阈值的同一模式
    永不进入候选。三档扫描实测后定为 0.75，见 §11.2
  · Stage2/3/4 照旧，全文输入（v2 已改造）
                            ↓
L3 · resolve_one 桶内二次归并【保留，不是冗余】
  L1 键换成 SPU 后，`resolve.l1_candidates` 在同一 SPU 内召回既有卡，
  L2 向量排序 + L3 LLM 判同。它是「同桶但 Stage1 分成两个模式名」的兜底——
  分桶只保证候选同桶，不保证同卡（审计 I6）。跨源同问题召回率是放行门槛之一
                            ↓
产出 · 问题卡：身份 = (SPU, problem_mode)
  · 跨 SPU 不合并、不去重
  · 拆分检测保留，在 SPU 内执行
                            ↓
收尾 · 快照 → 派生层刷新 → PM 放行（无跨源汇聚 LLM）
```

### 1.3 相对 v2 的改变与理由

| 改变 | 理由（均有实测支撑） |
|---|---|
| 分块键 云听标签 → SPU | 标签词表在两源间有裂缝（81 共有 / 87 独有），同一问题挂不同标签就进不同桶，L1 连候选都圈不到。SPU 是老品的天然业务单位，物理成立无裂缝 |
| 删除 `cross_source_merge` | 它是为标签裂缝打的补丁。分块换成 SPU 后来源天然混合，补丁失去存在理由。且其实现本就错误——双向复制证据、从不置 `merged_into`，两卡各持同一批证据、evi_total 双计（审计 I13/全量审计） |
| 收尾去跨源汇聚 | 跨源汇聚是收尾耗时最长的 LLM 环节。删除后收尾从实测 195–242 分钟大幅塌缩，且顺带消除该循环的串行瓶颈与并发竞态风险。**拆分检测与快照不受影响，仍保留** |
| 多 SPU 证据语义明确化 | v2 的笛卡尔扩散在 v3 下成为定义良好的行为：证据属于它提及的每个 SPU，且**每一行都记录归属来源** |

### 1.4 已知代价（业主已接受）

1. **`n_eff` / `scope` 对老品机会点失去意义**——它们度量跨 SPU 扩散，v3 下恒为 1。
   实测基线：当前 1,006 条老品机会点中 **780 条跨 SPU、226 条单 SPU**（最大跨度 91 个 SPU），
   v3 后这 780 条会裂成对应数量的 SPU 级问题卡。这是设计意图，不是回归。
   **连带影响**：`system/app/routes/strategy.py:19` 默认按 `scope='品线级'` 过滤，
   v3 下该视图为零行——必须按 §3 处置，不能让它静默显示 v2 旧值。
2. **`voc_spu_issue` 不退役，改为 1:1 投影**（v3.0 的「评估退役」已撤销，见 §4.3）。
3. **身份域重键**（opp_id 全换）。本来每轮 churn 98%，不构成新增代价。
   人工决策表（`voc_opportunity_manual` / `voc_spu_issue_manual` /
   `voc_status_log` / `voc_spu_issue_log`）当前均为 0 行，**是做此类重构
   最便宜的窗口**；但 `voc_proposal` 有 47 行（本轮 detect_split 机器产出，
   非人工裁决），且 `rerun_both.sh:294` 会 TRUNCATE 它。旧 ID 处置见 §9。
4. **人工状态的迁移是确定的，不是 1→N 歧义**（审计 I10 判定「未解决」，
   本条为订正——该判定基于「人工状态是机会点级」这一前提，而实测主键结构
   不支持该前提）。逐表核实（2026-08-19 生产库 `pg_constraint`）：

   | 表 | 主键 | 写入方 | v3 下的映射 |
   |---|---|---|---|
   | `voc_spu_issue_manual` | **`(spu, opp_id)`** | 产品页 `UPDATE_ISSUE_STATUS`、复活 `APPLY_REVIVAL` | **1:1**。一张跨 3 SPU 的旧卡在该表本就是 3 行，v3 裂成 3 张卡后逐行对应 |
   | `voc_opportunity_manual` | `(opp_id)` | 创新页 `UPDATE_INNOVATION_STATUS` | **1:1**。只存新品，而新品在 v3 下不裂 |
   | `voc_status_log` / `voc_spu_issue_log` | 代理键 `log_id` | 流水 | 按 `voc_opp_id_map` 改写 `opp_id`，重复是日志的正常语义 |

   **关键事实：老品的 PM 状态从来不是机会点级，而是 (SPU, 机会点) 级**——
   产品页写的就是 `voc_spu_issue_manual`。所以「一份决策裂成三份」的场景
   不存在；SPU 维度早就在键里了。

   **真正 1→N 的只有 `voc_opp_snapshot`**（主键 `(opp_id, week)`，实测 1,970 行）。
   它是机器产出的周快照，用途是 `check_revive()` 的基线。**处置：不迁移，
   v3 按 §7.5 的新分母重新生成**。代价是老品的复活检测缺一个周期的基线，
   下一周恢复；这是确定的、可接受的，不需要人工介入。

   四张人工表当前均为 0 行，上述规则本轮无事可做；但规则已写死，
   **施工时有行也照此执行，不需要停工确认**。

## 2. 新品创新管道 v3

### 2.1 目的

服务**创新页**，回答：**用户在要什么我们还没有的东西。**

### 2.2 流程

```
G1–G4 同上 → G5 无 SPU 的【诉求】进新品创新（无 SPU 的【缺陷】丢弃）
                            ↓
claim —— G4 从完整正文提炼的归一化诉求短句（「缺少/需要 + 对象 + 能力」，≤30字）
                            ↓
claim 向量预聚类（余弦 0.10，K=20，k-NN 图 + 并查集）【唯一去重层】
                            ↓
Stage1–4 生成 → 身份 = (新品创新, NULL, problem_mode)
```

### 2.3 改动一：身份契约冻结为 `core_tag = NULL`

**现状**：`pipeline.py:747-748` 对新品写 `core_tag = _no_placeholder(group["mode_name"])`，
而 `problem_mode = _specific_mode(obj, group["mode_name"])` 也源自同一个 `mode_name`——
两个字段近乎重复，**964 条机会点有 962 个不同 core_tag**。

**处置（冻结，不留给实施阶段选）**：新品 `core_tag` 固定写 `NULL`。
身份退化为 `(新品创新, problem_mode)`，语义正确——新品诉求本就不依附任何产品。

**为什么不是「保持 claim」**：claim 文本可变，归一化的微小差异就制造新身份，
重跑不幂等、快照不连续（审计 B4）。为什么「全 NULL 桶」不再是问题：
L1 对新品已按 §2.4 移除，没有任何查询会用 `core_tag` 给新品分桶。

**代价**：两个语义不同但 `problem_mode` 字符串相同的新品诉求会并成一卡。
预聚类已在上游按 claim 向量去重，此处并卡是期望行为而非缺陷；
探针须报告新品合卡数与合前后卡数差（§8.5）。

### 2.4 改动二：显式移除失效的 L 系列

**现状问题（实测）**：`pipeline.py:879` 对两个生命周期无差别调用
`resolve.resolve_one()`，而 L1 的分块键是 `core_tag` 字符串精确相等
（`resolve.py:23`）。最近一轮 run_log 实证：`resolve.l1_empty = 962`——
**L1 候选集几乎全空，L2/L3 从未被触发**。作为对照，老品迭代同轮 `l1_empty` 仅 168。

**处置**：`resolve_one` 按 `opp_type` 分流，新品创新直接返回 create，
不再进入 L1/L2/L3。理由是消除「看起来有去重、实际空转」的伪能力——
它每轮白跑 962 次 SQL 查询，且让人误以为新品有第二道去重保险。

### 2.5 改动三：墓碑抑制——明确放弃，不静默丢失

`lifecycle.check_tombstone()` 定义于 `lifecycle.py:76-92`，**全仓无任何生产调用点**
（`README.md:82`、`pipeline_redesign.html:195` 均已声明「仅定义未接入」）。
v3 让新品直接 `create`，会把这个缺口固化为显式行为（审计 B6）。

**处置（本次决策）**：**放弃墓碑抑制能力**。删除 `check_tombstone()` 函数，
同步删除 `README.md:82`、`system/README.md:86`、`pipeline_redesign.html:195`
中的相关承诺，`m4_lifecycle.py:9` 的免责注释一并清理。

**保留的**：`check_revive()`（基于快照的唤醒）不受影响，继续在收尾运行。
**记入待办**：「PM 置为不考虑的新品诉求下轮重复出现时的抑制」是一项独立需求，
需要新品侧的稳定身份（当前 `problem_mode` 逐轮 churn），本次不具备实现条件。
不得在任何文档中宣称墓碑抑制已生效。

### 2.6 不改的（已确认为特性而非缺陷）

- **散是本性**——诉求本来就长尾，业务已接受
- **0.10 紧阈值**——宁漏勿错，标定过（平台期 0.04–0.15）
- **不加源标签筛选器**——实测最大话题标签仅覆盖 3.5%，
  累计仅 41.5% 的池内消息带话题标签，筛选器会让过半卡片落空

## 4. 归属契约（本次新增的核心数据结构）

### 4.1 问题：派生层重新展开消息数组，产生四象限

`026_spu_layer_inherited.sql:51-85` 的 `voc_spu_issue` 定义中，SPU 来自
`CROSS JOIN LATERAL unnest(m.spu || m.spu_inherited)`——**从消息读，不从机会点读**。
v3 下一条 `spu={A,B}` 的证据会被路由到 `opp_A` 与 `opp_B` 两张卡，
派生层再各展开 2 个 SPU，得到 `(A,oppA)(B,oppA)(A,oppB)(B,oppB)` 四行——
**A 的产品页会显示 B 的问题卡**（审计 B1）。这是 v3 分块键变更引入的新缺陷，
v2 下因为 core_tag 是标签、卡本就跨 SPU，该展开是当时的正确写法。

### 4.2 处置：关系行携带归属，冻结于 run_id

`voc_opp_evidence` 新增三列：

| 列 | 类型 | 语义 |
|---|---|---|
| `assigned_spu` | `text` | 该证据行归属的 SPU。老品必填，新品为 `NULL` |
| `assignment_source` | `text CHECK IN ('fact','root')` | `fact`=云听从该消息本身识别；`root`=从组内原帖/视频继承。029 起继承只有原帖一个来源，故不再有 `inherited` 这个笼统取值 |
| `assign_run_id` | `text` | 产生该归属的运行 ID，用于快照冻结与回溯 |

约束与自检：

- 老品：`assigned_spu = (SELECT core_tag FROM voc_opportunity WHERE opp_id = oe.opp_id)`
  ——迁移与每轮收尾各跑一次全量自检，不等则整轮失败
- 新品：`assigned_spu IS NULL AND assignment_source IS NULL`
**归属快照冻结（审计 I11 判定「未解决」，本节为订正）**

v3.1 只写了「按 run_id 固定一次」这句话和一个关系列，那是文字约束不是机制：
`023_social_thread_columns.sql:64-77` 的继承函数是**全表 UPDATE**，
生成过程中任何人重跑它，`m.spu_inherited` 就变了，而路由、派生、页面各自
实时重读消息数组，会在不同时刻读到不同归属。必须落成**物理快照表**：

```
voc_assign_snapshot(
  run_id       text    NOT NULL,
  message_id   text    NOT NULL,
  seq          int     NOT NULL,
  assigned_spu text    NOT NULL,
  source       text    NOT NULL CHECK (source IN ('fact','root')),
  group_id     text,                      -- message_group_id，供 I3 继承污染追溯
  PRIMARY KEY (run_id, message_id, seq, assigned_spu)
)
```

- **一次性写入，永不 UPDATE**：生成开始时由一条 `INSERT … SELECT` 展开全部
  `spu ∪ spu_inherited` 并落盘；表上加规则或触发器禁止对已有 run_id 的行做
  UPDATE/DELETE（只允许整轮清理）
- **内容指纹**：`voc_run_log.metrics` 记录该 run_id 的
  `count(*)`、`count(DISTINCT (message_id,seq))` 与 `md5(string_agg(…))`；
  收尾前重算比对，不等则整轮失败。这是「冻结」二字唯一可验收的形式
- **单一读口**：本轮的路由、生成、派生层刷新、验收 SQL 一律 JOIN 本表，
  **不得再读 `voc_message.spu` / `spu_inherited`**。发布静态门：
  v3 代码路径中出现这两个列名即视为违规
- 事实 SPU 在本轮中途补标不影响本轮；下一轮重算，并按上一轮快照 diff
  输出受影响的 opp_id 列表
- `voc_opp_evidence` 的三列是快照的**投影**，便于消费方免 JOIN；
  与快照不一致时以快照为准，自检不等则整轮失败

## 5. 口径与守恒等式（新增，施工前必须先测）

审计 B2/B3/I2 的核心：v3 引入扇出后，「证据总数」不再是单一数字，
把两个口径混称会让四象限错误被当成成功验收。**定义四个量**：

| 量 | 定义 |
|---|---|
| **U** | 唯一事实数：冻结 G5 池中 `count(DISTINCT (message_id, seq))` |
| **F** | 扇出后应有行数：`Σ over (message_id,seq) of count(DISTINCT assigned_spu)` |
| **R** | 路由实际产出行数：进入 L1 分桶的行数 |
| **P** | 关系表落地行数：`count(*) FROM voc_opp_evidence WHERE 老品` |

**守恒等式（每轮自检，任一不成立则整轮失败）**：

```
R = F                    路由无缺失、无重复分配
P >= F                   一条证据可挂到同 SPU 的多张卡；但
count(DISTINCT (message_id, seq, assigned_spu)) = F
每个 opp 的 assigned_spu 唯一 = core_tag        零跨 SPU 问题卡
```

**报告口径（前端与指标同时给两个数，禁止混称）**：

- `evi_total`：机会点关系行数（热度）
- `unique_fact_count`：唯一事实键数 `count(DISTINCT (message_id, seq))`

### 7.4 统一 `has_spu` 口径（审计 I13 判定「未解决」，本节为订正）

v3.1 提了函数名却没给定义、没进文件清单、没定迁移顺序。**本节写死**：

```sql
CREATE OR REPLACE FUNCTION voc_has_spu(p_message_id text)
RETURNS boolean LANGUAGE sql STABLE PARALLEL SAFE AS $$
  SELECT EXISTS (
    SELECT 1 FROM voc_message m
     WHERE m.message_id = p_message_id
       AND COALESCE(cardinality(m.spu), 0)
         + COALESCE(cardinality(m.spu_inherited), 0) > 0)
$$;
```

现状裂缝（已独立复核）：`015_classification_contract.sql:76` 的
`has_spu` 只查 `cardinality(m.spu) > 0`，而 `classification.py:17-29`
查 `spu ∪ spu_inherited`。一条只有继承 SPU 的社媒消息，**Python 判老品、
SQL 判新品**，SQL 自检与运行时 `recount()` 会给出相反的生命周期。

**迁移顺序（不可颠倒）**：

1. 先建函数（纯新增，不影响任何现有查询）
2. 再改 015 的 `has_spu` 表达式调用它，重跑分类契约自检
3. 再改 018 / 026 的 `unnest` 段
4. 最后跑迁移测试，必须覆盖四种状态：
   **仅事实 SPU / 仅继承 SPU / 两者都有（冲突）/ 两者皆空**

**不得**把 026 已经覆盖继承当作 015 已经正确——它们是两条独立路径。

### 7.5 快照分母必须重写（审计 B10，已独立复核）

`run_generate.py:139,142` 两处分母均为
`WHERE e.is_product AND e.tag IS NOT DISTINCT FROM o.core_tag`。
v3 下 `o.core_tag='SPU-A'` 而 `e.tag='电池'`，两者永不相等——
**每张 v3 快照的 `base_total` / `neg_total` 都是 0**，周对比、墓碑基线、
任何依赖分母的报表都会把真实变化读成零。

**改法**：分母改为按 `assigned_spu` 过滤的 SPU 证据集合，按唯一

## 11. 第一轮探针结果（2026-08-19，只读，未写库）

脚本 `pipeline/scripts/probe_spu_bucketing.py`，全量 277 个 SPU 桶干跑 Stage1 +
`merge_similar_modes`，不跑 Stage2/3/4、不落库。基底为本轮生成期挂靠的老品证据
（`match_by IN ('rule','llm')`，排除 `cross_line`——那是 v3 要删的环节的产物）。

### 11.1 规模与耗时：结论与施工前的估算相反

| | v2 实测 | v3 探针实测 |
|---|---|---|
| 分桶 | 191 个标签桶 | 277 个 SPU 桶 |
| Stage1 批次 | 284 | 328 |
| **卡数（同一批事实）** | **1,006** | **1,450（+44%）** |
| 每桶平均卡数 | 5.7 | 5.2 |
| **Stage1 全量耗时** | — | **143 秒** |
| 探针全程 LLM | — | 631 次 / 587,563 tokens（约 ¥1） |

施工前按「每张跨 SPU 卡裂成其 SPU 数」推的上界是 4,357 张（4.33×），
**实测 1,450，上界高估 3 倍**——因为 SPU 桶内 Stage1 一次看到该 SPU 的全部证据，
把 v2 分散在不同标签桶里的东西合并掉了。

**耗时结论（这是本轮最重要的修正）**：
- Stage1 全量只要 143 秒，**不是瓶颈**
- v2 `generate_existing` 4h44m 的大头是**主线程里串行的持久化**
  （`pipeline.py:368-372`，`persist_opportunities` → `save_opportunity` → `resolve_one`）
- 收尾实测给出单次 L3 判定延迟：4,097 次调用 / 5h00m ≈ **4.2 秒/次**（纯串行）
- 每卡 L3 调用数 = `min(10, max(3, 0.3×同桶已有卡数))`（`config.py:183`），
  v2 每桶 5.7 卡、v3 每桶 5.2 卡，**两边都被 MIN=3 兜住**，所以串行段只随卡数线性增长

| | v2 实测 | v3 投影（串行） | v3 投影（持久化按 core_tag 分区并行） |
|---|---|---|---|
| 串行 L3 调用 | ~2,750 | ~4,270 | 关键路径 ~102（最大桶 34 卡×3） |
| 串行段 | 3.4h | 5.0h | ~7 分钟 |
| 收尾 | 5.0h | 分钟级 | 分钟级 |
| **整轮** | **9.7h** | **~5.5h** | **~30 分钟** |

**v3 即使不动并发也净赢**（9.7h → 5.5h）。并行化是高价值优化而非前置条件。
其安全性来自 `resolve.py:23-35`：L1 的 WHERE 是 `core_tag IS NOT DISTINCT FROM %s`，
不同 core_tag 的卡永远不可能互为候选，故可区内串行、区间并行，去重语义不变。

### 11.2 质量：跨源天然混合成立，漏合并是真问题

**成立的**——跨源同问题在 SPU 桶内自然合到一起，无需 `cross_source_merge`。
实例（SPU `MA39`，模式「手机夹磁吸强度不足」n=17）同时含电商中文原声
「手机太大的 根本就整不住 老掉」与社媒英文原声
「the holder detached and my phone fell directly」。

**不成立的**——`merge_similar_modes` 在热门桶只合掉 591 → 537（9%）。
按中文 2-gram Jaccard ≥0.3 扫同桶模式名，得 **32 对疑似漏合并，遍布全部 23 个热门桶**。
人工过一遍真假掺半，确凿的同模式被拆卡例子：

- `MA39`：「支架支撑长度不足」vs「支架整体长度不足」
- `2287`：「电池续航快速衰减」vs「电池续航时间短」
- `2575`：「角度调节机构过紧难操作」vs「铰链调节机构过紧难以操作」
- `SL03`：「闪光触发失效或不同步」vs「闪光灯不触发」

正确分开的例子（说明该启发式会过报）：`SL03` 的「闪光灯不触发」vs
「充电时误触发闪光」是相反失效。

这直接印证 §8.3 把**漏合并**定为主门槛：这些对全部卡在 `MODE_MERGE_COS=0.85`
之下，永不进入候选，L3 没有机会纠正。

**阈值扫描已完成（2026-08-19，277 桶全量各跑一遍）**：

| `MODE_MERGE_COS` | 卡数 | 合并数 | 疑似漏合并对 | LLM 调用 | 耗时 |
|---|---|---|---|---|---|
| 0.85（现状） | 1,450 | 56 | **32** | 631 | 143s |
| **0.75（选定）** | **1,395** | **111** | **12** | **744** | **148s** |
| 0.65 | 1,282 | 202 | 6 | 940 | 159s |

该阈值只决定**候选**，判同仍由 L3（`prompts.MODE_MERGE`）做，所以降低它是
「把漏掉的对子送进 L3 复核」，误合并由 L3 挡。**但 L3 不是完美闸门**——
人工抽查合并结果（对比高低阈值下消失的模式名）：

- **0.75 基本正确**：「塑料件占比高致质感与耐久疑虑 / 塑料材质质感廉价 /
  底座材质塑料感强」并为一张、「体积过大 / 重量偏大 / 重量过大影响手持 /
  便携性差」并为一张，都对。抽查 6 个热门桶只见 1 处可疑
  （MT44B「云台或角度调节自由度不足」并进「云台/夹持结构不稳」——
  调不动与晃动是两回事）
- **0.65 明显过度合并**：MT44B 把「伸缩杆**无锁定功能**」并进「刚性不足易弯曲」
  （缺件 vs 刚度）、MT85 把「底部结构单薄」与「上半杆体配重不足」并为一张
  （不同根因）、MA60 把「表面脏污疑似二手」也并了进去

**决定：`MODE_MERGE_COS` 0.85 → 0.75**，进 §7.2 改动清单。
代价 +18% LLM 调用、+5 秒，换漏合并降 62%。

**残留（不阻断，记入待办）**：0.75 下仍有 12 对疑似漏合并，且 L3 会放过
少量误合并。再往下的杠杆不在阈值而在 `prompts.MODE_MERGE` 的判定质量，
以及 `MAX_GROUP_SIZE` 上限导致的「想合但超限只能留两张」——后者降阈值无解。
本轮不动，留待 v3 上线后按真实卡片反馈迭代。

**方法学说明**：上表「疑似漏合并对」由中文 2-gram Jaccard ≥0.3 自动扫出，
会过报（「闪光灯不触发」vs「充电时误触发闪光」是相反失效，被误报为同模式）。
它只用于**同口径横向比较三个阈值**，绝对值不代表真实漏合并率——
真实率需 §8.2 的人审金集，那一项仍未闭合（审计 B8）。
