必须按 `001` → `015` 的编号关系理解，实际应用分两条路径：符合已核实 012 基线的存量库执行 `013` 后再应用 `014`；新库的当前 `001` 已直接建立新来源约束，不执行带固定 645 行断言的 `013`，但仍需在相应数据前置条件满足后建立其余结构并应用 `014`。`011/012` 是当前最终审计行为。`scripts/m0_deploy_pg.sh` 目前只执行 `001`–`004`，且扩展可用性检查仍列旧的 `pg_bigm/pgroonga` 而非实际使用的 `pg_trgm`，因此它**不能单独建立满足当前应用的完整数据库**。仓库没有自动迁移器，`011/012` 自检也依赖已有业务行。

**生产已应用基线是 `015`**。既有运维记录显示 `013/014` 于 2026-08-16 在生产库执行完毕：`013` 当时的自检结果为旧值残留 0、电商 207、社媒 438、总数 645，`014` 两列已建；同日以 `/home/sdy/voc-analytics` 工作副本重跑 W08–W32 抽取，记录为 25 周全部成功、错位 0。这些是沿用的历史事实，**本次阶段 2a 没有连库或远程复核**。**`015` 已于 2026-08-17 在生产库执行完毕**，事务内自检十项全部通过：老品迭代/确定 264、新品创新/确定 368、无效 13、总数 645、`classify_rule IS NULL` 为 0、`evi_total` 漂移 0、R0–R3 = 12/264/368/1。`voc_spu_issue` 由 161 条 / 51 卡变为 163 条 / 53 卡。执行后独立复核：23 条应用 SQL 全部真库 EXPLAIN 通过、五个页面与 SPU 详情页均 200、68 条社媒→老品迭代逐条核实确实挂着 SPU。其固定 645 行自检决定了它不能被当作空库通用迁移。

### 1.2 阶段 2a 分类契约与受控验收

分类只看一个机会点通过 `voc_opp_evidence` 挂载的**完整证据集**，不再用调用时的渠道参数决定 `opp_type`。规则按下表自上而下求值：

| 规则 | 条件 | 写入结果 | `015` 受控验收预期 |
|---|---|---|---:|
| R0 | 零条挂载证据 | `classification_state='无效'`，`opp_type=NULL` | 12 |
| R1 | 任一证据消息 `cardinality(spu) > 0` | `opp_type='老品迭代'`，`classification_state='确定'` | 264 |
| R2 | 无 SPU 且证据中有 `src_line='社媒'` | `opp_type='新品创新'`，`classification_state='确定'` | 368 |
| R3 | 无 SPU 且证据中有 `src_line='电商'` | `classification_state='无效'`，`opp_type=NULL` | 1 |

无 SPU 而同时含社媒与电商证据时，因 R2 先于 R3 而命中 R2。R0/R3 的「无效」是与 `opp_type` 正交的有效性标记，**不删除机会点或证据**；受控应用 `015` 且部署对应应用代码后，所有使用者看板读路都只取 `classification_state='确定'`，排查人员仍可沿原证据链诊断上游缺陷。

`015` 按 `voc_opp_evidence` 实际行数重算全部 `evi_total`，不信任旧统计值。`002_triggers.sql` 的 locked 行字段保护原本就将 `evi_total` 列入统计白名单；`015` 是正式演进该触发器契约，同时放行可回放的 `opp_type/classification_state/classify_rule`，不禁用或绕过触发器。受控验收应由迁移末尾的事务内自检确认：老品迭代/确定 264、新品创新/确定 368、无效 13、总数 645、`classify_rule IS NULL` 为 0，并确认 `evi_total` 与关系表行数无漂移。**上述数字已于 2026-08-17 受控执行并逐项复核通过。**

生成期先用当前分组的证据纯函数求值；挂载、跨线汇聚与 MERGE 都可改变最终证据集，因此证据关系改写与统一 `recount` 共用同一事务。`recount` 基于该机会点的全部已挂载证据回算，是权威结果；任一步失败均不应留下关系、分类或证据计数半更新。电商生成池同时排除 `cardinality(spu)=0` 的消息，因为它们是 R3 所指的上游数据缺陷，不应再产生新机会点。

`voc_spu_issue` 从 `015` 起改为只收录 `opp_type='老品迭代' AND classification_state='确定'` 的机会点，并仍只将实际挂有 SPU 的证据计入对应 SPU 卡。旧的 `m.src_line='电商'` 条件不保留：分类解耦后，若与新条件并存，会继续丢掉已挂 SPU 的社媒证据，与「SPU 挂载决定是否可路由」的口径相冲突。`HAVING count(*) >= 2` 阈值保持不变。

## 3. 常见故障处置

### 3.1 百炼相关

| 症状 | 原因 | 处置 |
|---|---|---|
| `type: "Arrearage"` | **账户欠费** | 充值。这把 Key 与智能客服项目共用，欠费会同时打挂两个项目 |
| `AccessDenied.Unpurchased` | 权限变更后的传播延迟 | **不是配置错误**。管线已带指数退避重试，等 1-2 分钟自愈 |
| `Access denied by API-Key restrictions` | 密钥的模型授权范围没勾选该模型 | 百炼控制台 → API Key → 编辑 → 访问模型范围 |
| `batch size is invalid` | embedding 批量超过 10 | 已在 `config.EMBED_BATCH=10` 限制，不应出现 |

> ⚠️ **跑大批量前先查余额**。历史教训：一次 26 周回填 + 多轮生成调试把余额跑干，连带打挂了客服项目。

### 3.2 云听相关

| 症状 | 处置 |
|---|---|
| 某分片 `matched_count=0` | 增量模式下 `voc_facts` 会抛错阻断（与“本周无数据”无法区分）。先检查过滤条件；当前代码没有“手工放行”开关，确需按回填语义处理时须走受控重跑并记录原因 |
| 触发 5000 条上限 | 管线自动二分重切，最多 4 层。仍失败说明单日数据量异常 |
| `openpyxl ParseError` | 导出 xlsx 含非法 XML 控制字符。管线已自动剥离，不应再出现 |

### 3.3 数据库相关

```bash
# 连接
docker exec -it voc-postgres psql -U voc_admin -d voc

# 三个角色（口令在 /etc/voc-analytics/runtime.env）
#   voc_writer — Dagster 作业用，可写机器表，人工表只读
#   voc_human  — PM/飞书回写用，可写人工表并裁决 proposal；不得写机器表
#   voc_reader — 只读，给 BI
```

**权限报错是正常的保护，不要用超级用户绕过**：
- `permission denied for table voc_opportunity_manual`（以 voc_writer 身份）→ 设计如此，机器不得写人工表
- `violates foreign key constraint voc_opportunity_manual_opp_id_fkey` → 人工决策行正在阻止机器删除，这是有意保护。当前合并执行器保留源机会点并写 `merged_into`，不要为绕过错误而清人工表；若确需销毁人工记录，必须另走有备份、有审批的人工数据处置流程

### 3.4 `rerun_both.sh` 清理失败语义

`scripts/rerun_both.sh` 的机会点层清理是一个不可分割的操作：所有 `TRUNCATE/DELETE` 由同一次 `psql --single-transaction` 包裹，并开启 `ON_ERROR_STOP`。任一语句因人工表外键或其他原因失败时，整段清理回滚并以非零状态退出；不得把「关系/快照/提案/血缘已提交，机会点删除失败」解读为正常保护结果。该事务性修复只做了静态代码复核，**本次未连库、未运行脚本，待受控验收**。

脚本现使用 `set -euo pipefail`。原本需要在局部失败后继续完成收集或清理的位置必须显式表达该语义：旧进程不存在、查无进程、日志尾部不可读等非阻断情况使用 `|| true`；两条并行生成线的 `wait` 各自显式捕获退出码，确保 A 线失败也会等待 B 线收束，随后统一判断，任一线失败就不执行收尾；跨线收尾也显式捕获并传递非零退出码。不应再依赖「命令失败但脚本继续」的隐式行为。

## 4. 告警与阻断

代码声明三个 **blocking** asset check；但实际口径与限制如下：

| 检查 | 阈值 | 含义 |
|---|---|---|
| `check_no_zero_match` | 最近 1 小时 failed run log 中含“零命中” | 实际零命中通常先令 `voc_facts` 失败；失败日志未成功写入时该 check 查不到，主阻断仍是资产失败。回填模式在导出层仅告警 |
| `check_volume_not_collapsed` | 最近一条成功记录低于之前四条成功记录均值 50% | 查询不保证五条来自不同周；少于五条记录时跳过 |
| `check_array_alignment` | 历史 ingest 错位累计值 / 当前证据总数 >1% | 不是“本周错位率”；非零时先核对累计口径再排查上游变化 |

一个非阻断 check：`check_stage4_reject_rate`。实现计算的是全库 `needs_review / 机会点总数`，阈值 40%，不是按本周或单次 Stage4 运行统计。

**连续两周触发同一项**：由系统 owner 与数据负责人共同评估，判断是上游变更还是本侧缺陷，决定是否暂停周度调度。

**安全类清单**：`voc_safety_watch` 只提供安全条目视图；仓库当前没有“本周新增”过滤、failure sensor、webhook 或飞书推送实现。推送质量负责人 + 产品负责人仍是待建立的运维流程，不能视为现有自动能力。

### 备份（pull 模型）


**为什么是 pull 而不是 push**：
1. ulanzicloud 的 `/etc/ssh/ssh_config` 存在既有故障（见 §7），出站 SSH 不可用
2. pull 模型本身更安全——生产机无权触达或删除异地备份

`voc_backup.sh` 的人工表单独备份包已于 2026-08-16 补全为六张：`voc_opportunity_manual` / `voc_status_log` / `voc_proposal` / `voc_spu_issue_manual` / `voc_spu_issue_log` / `voc_pm_pref`。新增人工表时必须同步加进 `HUMAN_TABLES`——这批数据不可再生。

> ⚠️ **2026-08-16 发现并已修复的备份空洞**：此前最新的“备份”产生于 8-14 库还空着的时候，全量包 9.2 KB、`pg_restore -l` 里 **0 条 TABLE DATA**，等于没有备份，而 `LATEST` 标记让它看起来是新鲜的。已重做并验证（18 MB / 14 条 TABLE DATA）。**教训：只看 `LATEST` 和文件存在性不足以判断备份可用，必须验证归档里确实有 TABLE DATA 条目。**

### 恢复演练（建议每季度一次）

```bash

```

演练脚本当前验证表/视图/触发器/索引的**数量**、五张核心表行数，并功能验证 `trg_voc_guard_locked`。它不覆盖角色与 ACL、两个人工状态层的 AFTER 审计、提案和 SPU 人工层数据语义；`pg_restore` 输出管道还会吞掉部分错误。这些是恢复演练的已知缺口，不能把脚本结果解读为全结构与全部触发器已完整验证。

RPO ≤24h 只是目标，前提是本地备份和异地拉取任务均已配置并验证；仓库内没有 cron/systemd timer，生产实际状态需运维核验。脚本的 `VOC_MAX_AGE_H` 默认 30 小时且超限只告警，不足以单独保证 RPO。RTO ≤4h 也是目标；历史“恢复 3 秒”只覆盖本地脚本计时，不含跨机传输，本轮未复测。

### 已知限制

1. **文本快照回滚不覆盖融合操作**：`voc_opp_snapshot` 只存机会点文本，不记 `merged_into`。文档历史快照记录过 20 条融合（8 条多源 + 1 条链式），但本轮未连库复核当前数量；这类融合不能靠文本快照精确回退。
2. **`VOC_AUTO_MERGE` 默认关闭**（`definitions.py` 的 `execute_proposals` 资产）。未经设计定稿评审不得置 1；开启属配置变更，需登记。

## 6. 回滚

`snapshots` 资产物化某个周分区时会写入 `voc_opp_snapshot`，支持按已存在的周快照回滚；受 §2 调度限制影响，不能仅凭计划定义断言每周都已生成快照：

```sql
-- 查某条的历史版本
SELECT week, title, prompt_ver, model_ver FROM voc_opp_snapshot
WHERE opp_id='OPP-XXXX' ORDER BY week DESC;

-- 回滚（受数据库触发器保护，见 pipeline/sql/002_triggers.sql；locked 条目不会被覆盖）
UPDATE voc_opportunity o SET
  title=s.title, problem_mode=s.problem_mode,
  desc_phenomenon=s.desc_phenomenon, desc_attribution=s.desc_attribution,
  desc_suggestion=s.desc_suggestion
FROM voc_opp_snapshot s
WHERE o.opp_id=s.opp_id AND s.week='2026-W32' AND o.opp_id IN ('OPP-XXXX');
```

**ulanzicloud 出站 SSH 完全不可用**：`/etc/ssh/ssh_config` 第 54 行写了 `permitrootlogin`——这是 **sshd** 的选项，误放进客户端配置，导致该机所有出站 SSH 报 `Bad configuration option: permitrootlogin` 并终止。

## 8. 容量与成本

实测（M0 QPS 压测）：

| 项 | 实测值 |
|---|---|
| embedding 批量上限 | **10**（25 直接报错） |
| embedding 延迟 | 0.81s / 批（10 条） |
| chat 单次延迟 | 1.54s 均值 |
| 并发 8 | 无限流，吞吐 5.15 次/秒 |

**当前代码默认 `LLM_CONCURRENCY=64`**（环境变量 `VOC_LLM_CONCURRENCY` 可覆盖；生产实际值本轮未远程核验）。上表是 M0 时期的旧基线；后续逐档探测记录的拐点：

| 并发 | 吞吐 | 结论 |
|---|---|---|
| 8 | 3.28 次/秒 | M0 初始取值 |
| 64 | **27.4 次/秒** | 拐点，采用 |
| 96 | 12.6–34.8 波动 | 已在边界 |
| 128 | 429 Throttling | 触发限流 |

共用密钥的欠费联动风险依然存在（见 §3.1），但 64 并发本身已验证不触发限流。

内存预算（宿主机 7,940 MB，可用 5,378 MB）：

| 项 | 预算 |
|---|---|
| voc-postgres | ~800–1,000 MB（shared_buffers 512MB） |
| Dagster 三进程 | ~480–540 MB |
| 峰值 2 run worker | ~800–1,200 MB（已配 `MemoryMax=1G`） |

余量约 2.7–3.3 GB，与 kol-dashboard 的 run worker 共享。若实测峰值逼近，把 `max_concurrent_runs` 降到 1。

## 9. 密钥管理

Python 代码只读进程环境，不会自动加载 `.env` 或 `.mcp.json`。systemd 服务通过 `/etc/voc-analytics/runtime.env` 注入。变量分组如下：

| 场景 | 变量 |
|---|---|
| 管道必需密钥 | `YUNTING_MCP_KEY`、`BAILIAN_API_KEY`、生产的 `VOC_PG_PASSWORD` |
| 管道可覆盖 | `YUNTING_MCP_URL`、`VOC_PROJECT_ID`、`BAILIAN_EMBEDDING_BASE_URL`、`VOC_EMBED_MODEL`、`VOC_CHAT_MODEL`、`VOC_LLM_CONCURRENCY`、`VOC_PG_HOST`、`VOC_PG_PORT`、`VOC_PG_DB`、`VOC_PG_USER` |
| 人工连接路径 | `VOC_PG_HUMAN_USER`、`VOC_PG_HUMAN_PASSWORD` |
| 危险开关 | `VOC_AUTO_MERGE`；仅值为 `1` 时开启，默认关闭 |
| Dagster 元数据库 | `VOC_DAGSTER_PG_USER`、`VOC_DAGSTER_PG_PASSWORD`、`VOC_DAGSTER_PG_HOST`、`VOC_DAGSTER_PG_PORT`、`VOC_DAGSTER_PG_DB`、`DAGSTER_HOME` |
| 建库脚本 | `VOC_ADMIN_PASSWORD`、`VOC_WRITER_PASSWORD`、`VOC_HUMAN_PASSWORD`、`VOC_READER_PASSWORD` |
| 异地拉取脚本 | `VOC_SRC_HOST`、`VOC_SRC_DIR`、`VOC_OFFSITE_DIR`、`VOC_MAX_AGE_H` |

当前 `m5_deploy_dagster.sh` 的 `rsync` 没有排除源目录 `.env`，之后又把它复制为 `runtime.env`，因此发布目录可能保留额外密钥副本；脚本还从 `/tmp/voc_pg.env` 读取管理员口令。部署前应把这两项视为已知安全缺口，核对文件权限与清理情况。规范目标仍是仅由 `runtime.env` 向进程提供密钥。

| 项 | 要求 |
|---|---|
| 轮转周期 | 180 天 |
| `runtime.env` 权限 | 0600，属主 `voc-analytics` |
| 泄露处置 | 轮转 Key → 查百炼调用日志 → **通知客服项目负责人**（Key 共用） |
| 可访问人员 | 需明确名单，记录在此 |
