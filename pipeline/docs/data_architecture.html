1数据从哪来

2四层结构

数据从原始文本到可跟踪的待办，要过四层。每层的单位都不一样，这是理解整套架构的关键——搞混单位就会把「一条评论」和「一个问题」当成一回事。

01抽取层 · 单位是「一句话里的一个标签」机器写

把每条评论按标签炸开成证据三元组：一个标签 + 一种情感 + 一段原声。一条评论平均产出 2.9 条证据，因为一条评论往往同时夸了外观、骂了吸盘。

148,876

voc_tag_taxonomy
7,722
标签树字典，两棵树

SPU 编码在抽取层一次性规范化：spu_raw 保留上游原值，spu 保存去除连字符与空格并统一大小写后的编码；抽取层不按任何名单筛选——云听依本公司产品体系打标，挂到 SPU 即本品，spu_unmatched 只留规范化后为空的无效 token。查询层直接消费规范值，不重复做正则清洗。

阶段 2a：分类由完整证据集的 SPU 挂载决定

机会点是老品迭代还是新品创新，决定因素是「能否通过 SPU 路由到具体产品 PM」，不是发现它的渠道。015 新增 classification_state text NOT NULL DEFAULT '确定' 和 classify_rule text 两列。执行迁移及后续分类时按下列顺序求值，先命中先生效；判定读取机会点的完整证据集合及其所属消息，不读生成入参里的单一 line。

规则条件（按顺序）opp_typeclassification_state目标数
R0在 voc_opp_evidence 中零条证据—无效12
R1任一证据所属消息 cardinality(spu) > 0老品迭代确定264
R2无 SPU，且任一证据来源 requires_spu=false新品创新确定368
R3无 SPU，且全部证据来源均 requires_spu=true—无效1

classification_state 只取「确定 / 无效」，与 opp_type 的「老品迭代 / 新品创新」正交；不给 opp_type 塞入第三个取值。classify_rule 记录本次命中的 R0–R3，供审计和回放。R0 / R3 只做无效标记，不删除机会点或证据；迁移后的所有使用者看板必须用 classification_state = '确定' 排除它们，排查端仍可保留完整证据链。

evi_total 以 voc_opp_evidence 的实际关系行数为唯一口径。015 对全部 645 个机会点重算该字段，不信任旧写入值；其中 12 个零关系机会点的目标值为 0。

✅

015 脚本的历史目标断言（本轮未复核环境结果）：确定的老品迭代 264，确定的新品创新 368，无效 13，总计 645，classify_rule IS NULL 为 0。这是脚本契约，不是本轮连库验证的结果。

阶段 2c：生成前按生命周期路由

generation_pool() 以真实 (message_id, seq) 为证据身份，按产品体验、「用户使用体验」负面、需求缺口和竞品对标等内容条件取数，不再维护电商/社媒两个并行池。每条证据先调用唯一的 classification.py 纯函数，再进入互斥的「老品迭代 / 新品创新」内容桶；Stage1、Stage2 提示词与 L1 候选键都只按 opp_type 选择。机会挂证后仍以完整证据集回算 R0–R3，该回算不取代生成前的互斥分流。

前置单条分类与完整集合分类并不等价：同义问题若由“有 SPU 的电商证据 + 无 SPU 的社媒证据”共同支撑，前者先入 R1、后者先入 R2，两个互斥生命周期不会合流；只有两条证据各自都命中 R1 时，当前老品桶才会跨来源合并。覆盖混合挂载场景需要新增 provisional 或跨生命周期规则，本阶段没有越权增加。

迁移 017 为 voc_opportunity 增加 source_lines text[] 和 evi_by_source jsonb，从证据关系回填完整供证来源；evi_by_source 中的计数合计必须与关系层 evi_total 对齐。旧 src_line 只作 legacy 单值代表：新建混合组取 sorted(source_lines)[0]，存量 recount 不改写原值；不得用它代替完整供证事实。新建机会的身份为 OPP2- + SHA-256 前 128 bit；老品与新品哈希均包含生命周期、规范化主题和问题模式，不含证据来源或 024 已移除的旧业务子类型；存量 OPP-* 不重键。

📊

静态池规模估算：旧社媒毛候选为 5,005 + 2,623 = 7,628 条消息；补回的「用户使用体验」为 3,249 条整桶、负面率 23.4%，毛新增约 3,249 × 23.4% ≈ 760 条，即毛候选约 8,388（+10.0%）。但多值标签重叠、low_conf、非空片段与业务门槛都会减少净新增，而新池是证据粒度，所以精确差异未验证；电商 4,232 是证据数，不能与社媒消息数直接相加。

当前仍有的来源限制：阶段 2a 只把 voc_spu_issue 改为按任何来源的实际 SPU 展开；voc_spu 容器和 n_eff 计算仍保留 m.src_line = '电商' 条件，本阶段没有对它们做渠道解耦。

为什么 148,876 条证据只挂出 1,638 条关系（迁移前快照）：绝大多数证据是正面或泛泛而谈的评价，构不成一个待解决的问题。挂靠出来的这 1,638 条里，负面 980 中性 404 正面 254——正面证据也会被挂进来，因为「别人夸的地方我们做得差」同样是问题的证据。

共性度：一个问题扩散多广

当前每个共性问题的 n_eff（有效产品数，Simpson 倒数）只使用电商来源的 SPU 挂靠计算，据此打上范围标签。n_eff = 1.82 意思是「在纳入计算的电商证据里，虽然涉及好几个 SPU，但抱怨主要压在其中不到 2 个身上」。阶段 2a 不改变这个口径，因此不能把它表述成已经覆盖带 SPU 的社媒证据。

6谁能写哪张表

权限不是配置，是数据库层面的硬边界。机器算出来的东西和人做的决定分表存放，各自只有一个角色能写，越界会被数据库直接拒绝。

角色能写什么写不了什么
voc_writer机器表：消息、证据、共性问题、挂靠关系、物化视图刷新任何人工表——只有只读权
voc_human人工表：状态、负责人、闭环理由、上市日期任何机器算出来的字段
voc_reader什么都写不了—

状态流转本身也由数据库的触发器把关，不靠应用层自觉：

  • 五个状态：考虑中 · 在跟进 · 项目中 · 已完成 · 不考虑，非法值直接被约束拒绝
  • 置为「不考虑」必须填理由，不填就报错——因为日后复议要靠它
  • 每次状态变更自动写审计流水，改了什么、谁改的、什么时候，跑不掉
  • 问题闭环后卡片变灰成墓碑；如果之后又有新反馈，需运行 system/scripts/check_revive.py 检测并复活为「待复议」——默认建议先用 --dry-run 只读预演，只有正式执行才会写库
💡

这套隔离是整个设计的地基：数据每周都要重算，但 PM 上周做的判断一个字都不能被冲掉。分表 + 分角色 + 触发器，三重保证。
