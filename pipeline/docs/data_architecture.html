2四层结构

数据从原始文本到可跟踪的待办，要过四层。每层的单位都不一样，这是理解整套架构的关键——搞混单位就会把「一条评论」和「一个问题」当成一回事。

01抽取层 · 单位是「一句话里的一个标签」机器写

把每条评论按标签炸开成证据三元组：一个标签 + 一种情感 + 一段原声。一条评论平均产出 2.9 条证据，因为一条评论往往同时夸了外观、骂了吸盘。

voc_message
50,902
消息本体、产品归属及其清洗留痕、国家、星级
voc_evidence
148,876
标签 × 情感 × 原声片段
voc_tag_taxonomy
7,722
标签树字典，两棵树

SPU 编码在抽取层一次性规范化：spu_raw 保留上游原值，spu 保存去除连字符与空格并统一大小写后的编码；抽取层不按任何名单筛选——云听依本公司产品体系打标，挂到 SPU 即本品，spu_unmatched 只留规范化后为空的无效 token。查询层直接消费规范值，不重复做正则清洗。

↓只有约 1.1% 的证据会挂到问题上——绝大多数是正面或泛泛评价，留在库里做产品全景
02消解层 · 单位是「一个共性问题」机器写

把散落在不同产品、不同渠道的同类抱怨合并成一个问题。判定链路是结构签名 → 向量召回 → LLM 裁定，产品无关——这样才可能发现「横跨 30 个型号的品线级毛病」。

03展开层 · 单位是「某个产品身上的某个问题」机器写 · 每周重算

共性问题 × SPU 交叉，该 SPU 在该问题上攒够 2 条证据才成一个条目。这是 PM 真正认领和跟踪的最小单位。两张都是物化视图，每周随生成自动重算。

↓物化视图每周被覆盖，所以 PM 的决定必须存到另一张普通表里
04人工层 · 单位是「PM 的一个决定」只有人能写

状态、负责人、闭环理由、上市日期都落在这里，与机器算出来的东西物理隔离——重算永远覆盖不到人的决定。目前 PM 机会看板已上线，由 system/ 中的 FastAPI 应用读取计算层、写入人工状态表，数据库触发器再记录审计流水。

0

voc_spu_issue_log
0

为什么 148,876 条证据只挂出 1,638 条关系：绝大多数证据是正面或泛泛而谈的评价，构不成一个待解决的问题。挂靠出来的这 1,638 条里，负面 980 中性 404 正面 254——正面证据也会被挂进来，因为「别人夸的地方我们做得差」同样是问题的证据。

这个问题在 MA39 这个 SPU 上攒够了证据，于是成为 MA39 卡片下的一个条目。PM 看到的是：MA39 这张卡上，「吸盘吸附失败」这个问题有 N 条证据——可以单独认领、单独跟踪、单独闭环。

注意标签与叶子不同名：标签是 吸盘，而它在树里的叶子节点是 手机夹。标签树的叶子是分类节点，具体标签挂在节点下面，检索时两个都可用。

共性度：一个问题扩散多广

每个共性问题算一个 n_eff（有效产品数，Simpson 倒数），据此打上范围标签。n_eff = 1.82 意思是「虽然涉及好几个 SPU，但抱怨主要压在其中不到 2 个身上」。

范围判据数量含义
单品n_eff < 1.592就那一个产品的事
多品1.5 – 353几个产品共有
品线级≥ 368整条产品线的通病，战略级信号
无 SPU 挂靠—432主要来自社媒，算不出扩散度

6谁能写哪张表

权限不是配置，是数据库层面的硬边界。机器算出来的东西和人做的决定分表存放，各自只有一个角色能写，越界会被数据库直接拒绝。

角色能写什么写不了什么
voc_writer机器表：消息、证据、共性问题、挂靠关系、物化视图刷新任何人工表——只有只读权
voc_human人工表：状态、负责人、闭环理由、上市日期任何机器算出来的字段
voc_reader什么都写不了—

状态流转本身也由数据库的触发器把关，不靠应用层自觉：

  • 五个状态：考虑中 · 在跟进 · 项目中 · 已完成 · 不考虑，非法值直接被约束拒绝
  • 置为「不考虑」必须填理由，不填就报错——因为日后复议要靠它
  • 每次状态变更自动写审计流水，改了什么、谁改的、什么时候，跑不掉
  • 问题闭环后卡片变灰成墓碑；如果之后又有新反馈，需运行 system/scripts/check_revive.py 检测并复活为「待复议」——默认建议先用 --dry-run 只读预演，只有正式执行才会写库
💡

这套隔离是整个设计的地基：数据每周都要重算，但 PM 上周做的判断一个字都不能被冲掉。分表 + 分角色 + 触发器，三重保证。
