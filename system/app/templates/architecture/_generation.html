两条互斥加工泳道

老品按产品聚合，新品按诉求聚类

两条线共享事实、分类与写卡质量框架，但组织单位和去重机制完全不同。基础机会不能跨生命周期或跨 SPU 强行合并。

Stage 1–4 的公共质量框架

  1. 1
    Stage1 模式切分

    给模型桶上下文和逐条证据上下文，产出成员分组；失败批次单独记账。

  2. 2
    Stage2 原型正文

    生成标题、现象、归因与 problem_mode；同一步执行程序校验和 grounding。三轮仍有非 grounding 问题时可带 needs_review 落库。

  3. 3
    Stage3 改进建议

    读取本卡正文与固定 20 条历史上下文，单独生成建议并校验；三轮仍失败则整组作废。

  4. 4
    Stage4 独立复核

    LLM 作为旁路审阅者记录硬 / 软问题；它不决定 needs_review，非 fatal 调用失败降为提示。

新品预聚类的四条守恒线

目标证据行 = 实际输入行 输入单元 = embedding 成功 + 失败单元 簇成员单元 = 全部输入单元 计划新品桶数 = 实际簇数

普通 embedding 批失败会让该批每个消息单元成为单例簇；只有失败数 > 2 且失败率 > 20% 时才视为系统性失败。鉴权 / 配额类 fatal 从不降级。

机器变化如何进入人工语义

  • MERGE多候选或安全类不自动挂接；即使开启自动接受，也只处理相关卡都没有 manual 行且非安全的提案。源卡保留 merged_into 与血缘。
  • SPLIT当前执行器主要写血缘 / 解除抑制，并不完成证据的真实重切分。
  • REVIVE已关闭机会出现显著新证据时生成复活建议，不自动改回进行中。
  • REWRITE需要重写语义时进入有限提案，而不是覆盖 PM 已接管内容。

默认关闭VOC_AUTO_MERGE 不会自动把 pending MERGE / SPLIT 标成 accepted；已经人工接受的提案仍会在下一轮生成前执行。

当前五状态与人工写入

考虑中↔在跟进↔项目中↔已完成↔不考虑
  • 状态跳转数据库校验合法枚举，但当前没有严格的状态转移矩阵，五种状态可直接切换。
  • 不考虑数据库触发器要求理由。
  • 待复议不是第六状态，而是“考虑中 + revived_at”的展示语义。
  • 每次变化写状态日志，保存 actor 与时间。
  • 当前缺口缺人工行也显示为“考虑中”，无法区分从未批阅和 PM 主动选择考虑中。

待改造“首次打任一状态即接管”需要独立 first_reviewed_at，现有锁定语义尚不满足。

复活目前有两条实现路径。 pipeline 的机会级检测只生成 REVIVE 提案；system/scripts/check_revive.py 是另一个 SPU 级人工 CLI，可直接把符合条件的问题改回考虑中。它没有内置调度，两套口径尚未合并为一个统一状态事件。
