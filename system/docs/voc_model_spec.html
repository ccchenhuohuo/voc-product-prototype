VOC 机会模型规格

两层结构、两类卡片、两条互相隔离的生命周期。老品迭代与新品创新分别运转；PM 已接管的 locked 行不在两者之间转换。SPU 是长期挂载的容器，问题是有生死的条目。

规格 v1 · 2026-08-15 历史数据快照 · 2026-08-17 阶段 2c 代码契约 · 仓库迁移链已到 027；实际环境版本以迁移记录为准

1两层结构

ℹ️

来源口径说明：voc_message.src_line 是 voc_source_policy 中已登记的证据来源；voc_opportunity.src_line 只是 legacy 单值代表，新建混合组取 sorted(source_lines)[0]，存量 recount 不改写。完整供证事实使用 source_lines 与 evi_by_source。当前策略种子为电商、社媒与待接入的问卷调研；机会点身份不含来源字段。

阶段 2a 分类契约：看完整证据集，不看渠道

老品迭代能路由到具体产品负责人，新品创新进入共享池；决定能否路由的是机会点全部已挂载证据中是否存在 SPU，而不是生成入口或 src_line。规则严格按 R0 → R3 顺序求值，先命中先生效：

规则完整证据集条件opp_typeclassification_state存量测得
R0voc_opp_evidence 中零条证据无可判类型无效12
R1任一证据所属消息 cardinality(spu) > 0老品迭代确定264
R2无 SPU，且任一证据来源 requires_spu=false新品创新确定368
R3无 SPU，且全部证据来源均 requires_spu=true无可判类型无效1

完整证据集仍按上述优先级处理：任一条挂 SPU 即 R1；全部无 SPU 时，任一来源 requires_spu=false 即 R2，否则 R3。生成期则先对每条证据用同一纯函数求值，形成互斥生命周期桶；关系写入后再按完整集合回算。「用户使用体验」只是入池内容规则，有 SPU 才是老品，无 SPU 仍按来源策略判定。

两次求值存在明确边界：同义问题若由一条有 SPU 证据和一条无 SPU 社媒证据支撑，逐证据阶段分别命中 R1/R2，互斥生命周期不会合流；完整集合的“任一 SPU 即 R1”无法倒推改写已分流的证据。当前跨来源老品合流只保证各证据本身均为 R1 的场景；混合挂载场景需另定 provisional 或跨生命周期规则。

🧾

有效性与类型正交：opp_type 仍只有「老品迭代 / 新品创新」，classification_state 只有「确定 / 无效」，classify_rule 记录 R0–R3 供审计与回放。无效机会点及其证据一律保留，所有使用者看板查询必须排除 classification_state = '无效'，诊断侧仍可追查完整证据链。

迁移状态：仓库链已到 027；本轮未连库核对各实际环境版本。「确定老品 264、确定新品 368、无效 13、总计 645、规则为空 0」是 015 脚本的历史自检断言，不是本轮复核的生产结果。

阶段 2c 生成身份与失败契约

统一内容池之后，Stage1 / Stage2 提示词与 L1 候选键都只按 opp_type 选择。新建机会使用 OPP2- + SHA-256 前 128 bit；身份材料与 L1 唯一域一致：老品与新品都由规范化的版本、opp_type、core_tag 与 problem_mode 构成，不含证据来源、业务来源列、周次或模型版本。024 已移除旧业务子类型字段。存量 OPP-* 不重键，消解命中时继承已有 canonical ID。

Arrearage、鉴权失败和硬配额/余额不足会立即打开熔断，不重试、不继续；同一 run 的两个生命周期进程通过原子共享文件传播首因。Stage1 的计划/完成/失败/取消批次及条数写入 run log；账本不闭合或任一生成进程非零时，禁止跨来源汇聚、拆分、快照和放行收尾。监督脚本要求 Bash ≥5.1，并在任何停止/清库动作前检查版本。

统一池的静态毛估：旧社媒候选为 5,005 + 2,623 = 7,628 条消息；「用户使用体验」3,249 条整桶 × 23.4% 负面率 ≈ 毛新增 760，毛候选约 8,388（+10.0%）。这不是机会点新增数；多标签重叠、low_conf、非空门槛与消息/证据粒度差异使精确净增未验证，且不得与电商的 4,232 条证据直接相加。

核心判断：状态机是项目生命周期——「在跟进 → 项目中 → 已完成」隐含有人立项、有版本交付。用这把尺子量，跨 30 个型号的共性问题不可能有一个项目能"完成"它，强行入机只会变成看板上的僵尸。

战略层不是死胡同：状态为「确定」的老品机会会通过 voc_spu_issue 按 SPU 自动展开为执行条目。当前应用没有「从战略问题手动派生卡片」的写入口；状态为「确定」且命中 R2 的机会点以 opp_type = '新品创新' 进入共享池。

原生 VOC 不是一层

原始 VOC 的浏览由数据服务商的 SaaS 承担，本系统不复制这个能力。14.8 万条证据单列成模块，只会制造巨大的信息量而没有实际用途——PM 不需要一个「所有 VOC 列表」页。

在本系统里，原生 VOC 只作为具体机会的支撑材料出现：问题条目详情列出该 SPU 下的全部原声（见 §4），新品创新详情按互动量与发布时间展示最多 3 条「灵感来源」。入口永远是某个具体问题或诉求，而不是一个 VOC 库。

🚫

明确的非目标：不做 VOC 检索页、不做全量证据浏览、不做原始数据导出。这些是 SaaS 的活，重复建设只会让 PM 在两个系统里看同样的东西。

3问题条目的生命周期

五态 = 考虑中 · 不考虑 · 在跟进 · 项目中 · 已完成，与一期一致。「灰化」是「已完成」的展示形态，「复活」是状态转移（回到考虑中并带 revived_at 标记，界面上呈现为「待复议」）——都不是新增状态。复活有两种触发，第二种是整套设计里最有价值的一环。

考虑中→ 在跟进→ 项目中→ 已完成+ 上市日期 灰化⟳ 新反馈 → 复活

上图是常见业务路径。数据库只校验状态值，当前页面也允许直接选择任一状态，并不强制只能相邻转移。

触发一 · 不考虑 → 证据涨到 3 倍

当初判「证据不足」，现在够了。迁移 009_spu_layer.sql 建立该规则，011_audit_after_trigger.sql 保留校验与赋值并把审计记账移到 AFTER 触发器：条目转为「不考虑」时，把当时的证据数写入 voc_spu_issue_manual.baseline_evi_count。system/scripts/check_revive.py 在当前证据数达到该基准的 3 倍时将条目复活；若操作者再次选择「不考虑」，触发器会用当时的证据数重置基准。

触发二 · 已完成 → 上市后仍有新反馈

改了但没改好。不需要 3 倍阈值——改动上市后任何一条同类抱怨都是信号。

⚠️

分界线必须是上市日期，不是标记「已完成」的日期。改动要过一段时间才上市，中间收到的都是存量反馈，拿标记时间当界会产生大量假复活。SPU 问题使用 voc_spu_issue_manual.target_release 与 release_date。新品创新的 voc_opportunity_manual 也有同名字段，但当前复活脚本不处理新品创新，不能视为已具备同样闭环。

问题条目 → 已完成 → PM 填「v2.1 / 2026-10-15 上市」
                              ↓
        publish_time > 2026-10-15 的同类 VOC → 复活 →「改动未生效」

这一步把系统从发现问题升级成验证改动有效性：PM 能拿到自己那次迭代到底管不管用的实证。这是别的 VOC 工具给不了的东西。

判定权

当前 Web 页面要求操作者手动选择「已完成」并填写上市日期；系统尚未接入认证，数据库触发器本身也没有为该状态强制 release_date 非空。机器不做自动闭环——它不知道改动是否真的上线。复活检测目前是独立脚本，应用与仓库都没有内置周期调度；在 system/ 目录可运行 python scripts/check_revive.py --dry-run 只读预演。

三条约束

  1. 不分二级。问题条目就是最小的分析单位，其下只有原声。
  2. 原文在上、译文在下。外语原声保留原文——它是最有说服力的素材；译文弱化显示供快速理解。
  3. 读数是元信息，不是分类。当前页面展示证据数、近 60 天新增、原声均星、有效产品数；每条原声附平台、星级、国别与发布时间，不构成分组结构。
⏱️

当前时间信号：证据带 voc_message.publish_time，页面按该字段倒序并汇总近 60 天新增。按月份聚集、批次或供应商归因尚未在应用中自动计算，不能把它写成现有能力。
